 2026-09-10 - THE GENERATED QC LAUNCHER NOW WRITES A LOG
--------------------------------------------------------------------------------

Station QC-STATION had no QC backend log at all, which is why both of the
2026-09-09 faults - an unopenable Quality Check page and a 400 on the Completed
tab - had to be diagnosed from a client-side error banner. The Run key launches
`pythonw.exe`, which has no console, so every line the backend wrote was
discarded. A log was added to the running process on the day, but the launcher
this service generates had no redirection, so it was gone at the next logon.

- New `qcBackendLogPath()`: `%USERPROFILE%\LWCAM_DBs\qc_backend.log`, beside
  `qc_engine.log`, `scrcpy.log` and `lwip\runtime\deskew_crop.log`, in the same
  folder as the node config. This follows LWCAM's own `QcEngineService._log`,
  which writes `qc_engine.log` there for the identical stated reason: a release
  exe has no console, so a field failure would otherwise be invisible.
  `%LOCALAPPDATA%\LWCam\QC` is deliberately NOT used - SETUP_QC.bat and the
  backend's node_config.py reserve that tree for caches (previews, qc_work,
  qc_audit, ai_review), and a log there would break that split.
- `writeQcBackendLauncher` redirects stdout and stderr to it, INSIDE the
  existing `__main__` guard. That placement is load-bearing for the same reason
  `uvicorn.run`'s is: the export's ProcessPoolExecutor re-executes this file in
  every worker, and they must not each reopen the same handle. The setup lines
  stay outside it, unchanged.
- One handle for both streams (`sys.stderr = sys.stdout`), line-buffered, so
  access and error output interleave chronologically instead of two handles
  racing over one file. Matches qc_engine.log being a single file.
- Bounded by one size check: over 10 MB, the old file is rotated to `.old`, so
  the pair caps at roughly 20 MB. A RotatingFileHandler through uvicorn's
  log_config is tidier and about triple the code.
- `errors="replace"`, and the whole block is wrapped in `except OSError: pass`.
  A traceback carrying an odd byte, or an unwritable folder, must not stop the
  server starting - the log exists to report failures, not to cause one.

TESTS: 139 passing, up from 136 (test/services/qc_backend_autostart_test.dart).
Asserts the log path is in the generated launcher, that it is NOT under
LOCALAPPDATA, that both streams share one handle, that the redirect sits AFTER
the `__main__` guard, and that it sits BEFORE `uvicorn.run` - otherwise
uvicorn's own startup output, the part that names a bad config, is lost. Same

Pairs with the LWCAM change of the same date: the QC task list now skips a

 2026-09-09 - STATION SETUP'S SAVE NOW ACTUALLY RESTARTS LWIP
--------------------------------------------------------------------------------

Saving Station Setup started LWIP but could never REPLACE a running one, so a
changed setting did not take effect until the next logon. startLwipNow only
starts, and a live instance holds work_root\orchestrator.lock - the second
process took no lock and exited by itself, which its own comment describes as
the intended guard. It is a fine guard and a bad restart: LWIP reads its config
once at import. Same defect the QC engine had, fixed the same way on
2026-09-04.

It also mattered for upgrades. Setup used to leave LWIP running on purpose, so
after an upgrade the save was the only thing that could have replaced the live
pre-upgrade process - and it could not. A station ran pre-upgrade LWIP through
two reinstalls on 2026-09-09 because of it; see LWCAM's CHANGELOG for the
LWIP-side and installer-side halves.

- New `stopLwipNow` (services/lwip_autostart_service.dart): writes LWIP's stop
  file, then waits for it to drain. LWIP finishes the folder it is already
  publishing and cancels the rest; dropped folders are not journalled, so the
  next run reprocesses them.
- The wait acquires LWIP's OWN orchestrator.lock rather than enumerating
  processes - the same `RandomAccessFile.lock` pattern as FileLockService.
  Holding the lock IS the proof the orchestrator has exited.
- The stop file is written to both `work_root\stop.request` and
  `%ProgramData%\LWCAM\lwip.stop`, because the installer needs the second one:
  work_root is under %USERPROFILE% and an elevated install cannot be relied on
  to resolve the operator's profile.
- The save now stops before starting, UNCONDITIONALLY: turning processing off
  has to stop the running instance too, not merely unregister the autostart.
- On a 90s timeout the save does not start anything - a process spawned against
  a held lock exits instantly and would report success. It surfaces the
  existing `lwipAutostartWarning` instead, saying processing is still busy and
  will start at the next logon.
- The stop files are deleted in a `finally`, always. The first version of this
  did not, and it took image processing down on a real station: the save stopped
  LWIP, started a replacement, and the replacement read the request still
  sitting on disk and exited 2ms after logging "Watching". A running LWIP
  consumes the file itself, so the cleanup is usually a no-op - it matters
  exactly when nothing was running to read it, which is also the case where the
  wait returns instantly and a replacement is started straight away. LWIP now
  also discards a request that predates its own startup, so neither side is a
  single point of failure.

 2026-09-03 - EXPORT WORKER COUNT IS A STATION SETUP FIELD
--------------------------------------------------------------------------------

The QC export now converts and hashes images across several worker processes
instead of one at a time (about three times faster on real scans). It sizes
itself from the hardware using the same rule as LWIP - every core but one - and
this field is how a station overrides that.

- New QC field: "Export workers (0 = auto)", written to lwcam_node_config.json
  as `exportWorkerCount` and read by the QC engine as `export_worker_count`.
  Disabled when QC is not installed on the PC, like the other QC fields.

- Why it exists rather than being left on auto: LWIP sizes itself by the same
  rule, so a station where both run can end up with two pools of cores-1 workers
  competing for the same cores. Neither breaks, but both slow down. Setting a
  number here is how an operator gives the export a smaller share.

- Out-of-range values are clamped by the engine rather than rejected here. The
  box is free text, and a settings value that fails validation on the engine
  side would stop the QC backend from starting at all - QC down over a typo.

- FIX, found while testing the above: the generated QC backend launcher
  (runtime\qc_backend_autostart.py, invoked by the logon Run key) now guards
  uvicorn.run behind `if __name__ == "__main__":`. That launcher runs as a
  script, so it IS __main__, and Windows spawns each export worker by re-running
  the main module - unguarded, every worker started its own uvicorn, blocked on
  port 8080 instead of converting its image, and the export died with
  BrokenProcessPool. It would have failed only on an INSTALLED station: the two
  other launch paths (START_QC_BACKEND.bat and LWCAM's sidecar) both use
  `python -m uvicorn`, which multiprocessing skips re-running. LWIP's launcher
  has always had this guard; the QC one never needed it until the export began
  spawning processes. Saving Station Setup rewrites the launcher, so an existing
  station picks the fix up on the next save.

 2026-08-28 - CROP PADDING IS A STATION SETUP FIELD, READ FROM ONE SOURCE
--------------------------------------------------------------------------------

LWIP's crop padding - the pixels kept on each side of the detected content rect
before cropping - was a literal in three unrelated places: the config writer
here, the bundled standalone config, and the benchmark harness. Changing it
meant finding all three and hoping nothing else had its own copy.

It is now a Station Setup field, and the generated deskew_crop_config.json is
the single source every consumer reads.

- NodeConfig gains processingCropPadding (default 200, was 40 before today).
  Added to BOTH apps' copies of the model: LWCAM reads the same file and can
  rewrite it, and a key its model did not know about would be dropped on that
  write, silently reverting the padding.
- Station Setup's LWIP section gains "Crop padding (pixels kept on each side,
  0 = crop tight)". lwip_config_writer reads config.processingCropPadding
  instead of pinning a number.
- lwipConfigProblem now rejects a negative padding, mirroring the rule python
  enforces at load. Without it a typo left a crash-looping watcher on the
  capture PC instead of a message on the screen where it was typed.
- 0 is a meaningful value (crop tight to the detected edge) and is preserved,
  never treated as "unset" and replaced by the default.

 2026-07-21
--------------------------------------------------------------------------------

- INITIAL RELEASE. PostgreSQL (schema v2 — see "LWCam Workflow & SQL update/
  LWCam_database_20260720.sql") is the source of truth for users, projects,
  and app_settings; this app is the ONLY writer of those tables. LWCAM only
  ever pulls them (read-only, plus a tiny 3-call PG write whitelist for
  password-change/login-stamp/has-data on its own side).

- AdminStoreService (lib/services/admin_store_service.dart) reconciles
  PostgreSQL-first with a local-JSON offline fallback (lwcam_users.json,
  same file and default directory LWCAM's sync pull reads). Every mutation
  reconciles first (pull-before-transform, so an online edit is never
  applied on top of a stale local copy), applies validated changes
  (device-ID/project-name/location-code uniqueness checked locally now,
  matching PostgreSQL's UNIQUE constraints the old NAS-only UI never
  checked), then pushes+pulls when online or queues offline
  (dirty + tombstone, auto-pushed on reconnect by a 30s status timer).

- Schema v2: users gained device_id (UNIQUE) and roles (comma-joined global
  roles — read back from users.roles, not re-derived from user_projects, so
  a zero-project admin keeps their role); projects gained project_key (the
  stable identity every upsert now conflicts on, since project_id is a
  human-editable label an admin can rename freely); a new app_settings
  key/value table holds metadata-keying/shutter/default-temp-password
  settings that used to live only in the NAS JSON.

- SuperAdmin login (lib/auth/super_admin.dart, byte-identical to LWCAM's
  copy) verifies against, in order: PostgreSQL's password-hash override →
  the local snapshot's copy of it → the factory hash — works on a
  brand-new PC with zero PostgreSQL connectivity, which is the intended
  fresh-station bootstrap path: run a portable build once, use Station
  Setup to write lwcam_node_config.json (the same file LWCAM's own
  SyncBootstrap reads) and seed the initial lwcam_users.json snapshot.

- Admin-viewable passwords do not exist (there is no passwordEnc field at
  all) — User Management can only reset a password to the shared default,
  matching LWCAM's own retirement of the feature on its side of the split.

 2026-07-21 (review pass)
--------------------------------------------------------------------------------

Findings from a three-way review (cross-app contracts, LWCAM sync/auth,
this app) — all verified against the code before fixing:

- FIXED (critical): pushSnapshot now applies delete-tombstones BEFORE the
  upserts (and recreating a deleted username drops its queued tombstone in
  the store too). Previously an offline delete-then-recreate of the same
  username pushed the new account and then soft-deleted it in the same
  transaction — the account silently vanished everywhere on the next pull.

- FIXED (critical): recreating a deleted project (or reusing a deleted
  user's device ID) no longer wedges sync permanently. Soft-deleted rows
  kept their UNIQUE-constrained values, so the recreate's INSERT hit a
  unique violation on the dead row and every subsequent push failed
  forever. Schema: users.device_id / projects.project_id / project_name
  switched to PARTIAL unique indexes (live rows only). country_location_
  code stays full UNIQUE (FK target from devices) — projectSoftDeleteSql
  now frees it by rewriting it to '~deleted~<id>' instead (the devices FK
  cascades; a still-bound device stays blocked until reassigned, as it
  should). DROP AND RECREATE the database from the updated SQL file.

- FIXED (major): the 30s reconcile timer (SyncStatusController) was never
  registered — queued offline edits never auto-pushed on reconnect and the
  Home status banner never updated on its own. Registered at startup.

- FIXED (major): a dirty offline push could regress PostgreSQL fields LWCAM
  owns — most seriously a capture user's self-changed password (the stale
  whole-store snapshot carried the old hash). The user upsert's DO UPDATE
  no longer touches password/must_change_password at all; explicit admin
  resets (and recreates of deleted usernames) go through a new targeted
  reset statement driven by a pendingPasswordResets queue in the store,
  and projects.has_data is now monotonic (OR, never back to false).

- FIXED (major): the Home status banner froze on its pre-save state after
  any Station Setup save (it was bound to the deleted service instance's
  Rx). It now re-binds via a bootstrap generation counter.

- FIXED (major): the Devices screen gated on LWCAM's capture-outbox
  syncEnabled flag (defaults false, no UI here) — dead on every admin-only
  station. Now gates on this app's own pgConnectionEnabled + host.

- FIXED (major): Station Setup rendered blank/default fields on its first
  open per app run (async config load vs initialValue text fields) — an
  admin could re-save defaults over a configured station. The form now
  waits for the load, and every open re-reads the file from disk (LWCAM
  shares it and may have rewritten it).

- FIXED (minor): startup no longer blocks the window behind the initial
  PG reconcile (~5s connect timeout when the host is unreachable); the
  trySync pull-write now takes the same .lock as mutations (shared-folder
  multi-admin edge); list parameters are now explicitly typed as text[]
  (was relying on driver fallback behavior); Project IDs may no longer
  contain '|' (the user_projects pair-encoding separator).

 2026-07-21 (later)
--------------------------------------------------------------------------------

- (Later tweak: the toggle was moved to the TOP of the PostgreSQL
  connection section, above the Host field, and retitled "Enable
  connection" — its state is the first thing an admin should see/set.)

- Station Setup gained a "PostgreSQL connection" toggle
  (NodeConfig.pgConnectionEnabled, default true). Previously the only way
  to stop AdminStoreService's automatic PG reconcile was to blank out the
  host, losing the saved credentials. The toggle lets an admin keep them
  configured but stop connection attempts — trySync() now skips the probe
  entirely when off, going straight to the same offline-queue branch a
  real unreachable PG uses. Intended for a genuinely permanently-offline
  site, or for testing offline behavior without discarding config. The
  Home status bar shows a distinct "PostgreSQL connection disabled" line
  (informational, not a warning) instead of the ordinary "Offline" one.
  LWCAM never reads this field.

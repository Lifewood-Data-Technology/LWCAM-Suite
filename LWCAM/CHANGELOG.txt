================================================================================
 LWCAM (Lifewood Capture) - CHANGELOG
================================================================================

- Forked from LifeTrans (life_transfer) on 2026-07-14, keeping legacy Normal
  Mode + Box Mode and dropping Rework Mode entirely; see AGENTS.md "History"
  for the full rationale. Entries below this point predate the fork and
  describe the combined app; entries from 2026-07-14 onward describe LWCAM
  alone (its sibling LWRework has its own CHANGELOG.txt from the same point).

--------------------------------------------------------------------------------
 2026-09-28 - REWORK FINDS THE ORIGINAL UNDER THE IMAGE DESTINATION
--------------------------------------------------------------------------------

- `ReworkService.inputFileFor` no longer reads the two "LWIP folders" from
  Station Setup. It takes the `<YYYYMMDD>\<folder>` tail of the
  `folder_path` LWIP recorded and looks under `destinationPath` - the folder
  this station copied the originals into, which IS LWIP's input. The old
  fields had to hold LWIP's output root spelt exactly as LWIP's own PC spells
  it, while Station Setup labelled them "as this PC sees them", so on a split
  site a recapture silently could not find its file.
- The date is searched from the end and must have a folder after it, because
  a Volume (the folder name) can itself be eight digits.
- Returns a file only when it exists: a recapture REPLACES an original, and a
  folder captured on a station with another destination is not here to
  replace. `effectiveInputRoot`/`effectiveOutputRoot` are deleted;
  `processingInputRoot`/`processingOutputRoot` stay in `NodeConfig`
  round-trip only.
- Tests: rework_service_test.dart rewritten against real files (5).

--------------------------------------------------------------------------------
 2026-09-25 - LWIP RUNS STANDALONE; LWCAM STOPS SUPERVISING/REPORTING IT
--------------------------------------------------------------------------------

- LWIP moves to its own machine as a boot-time SYSTEM service and reports each
  finished folder straight to PostgreSQL itself. LWCAM no longer supervises it,
  no longer tails its local `state.json`, and no longer enqueues the
  `capture_folder_processing` outbox row. Deleted: `processing_bootstrap.dart`,
  `processing_report_service.dart`, `lwip_service.dart`, their call sites in
  `main.dart`/`auth_controller.dart`/`capture_box_list_page.dart`, and
  `UploadStatsDB.recordFolderProcessing`/`isProcessingReported`/
  `recordProcessingSkip`/`migratePendingProcessingOutbox`. The "processing-only
  PC" concept (a `'PROCESSING'` pseudo device id for a PC running LWCAM only to
  report LWIP's work) goes with it.
- `NodeConfig.processingEnabled`/`processingWorkers`/`processingCropPadding`/
  `processingCloudReport` are round-trip only now — LWIP's own config file
  decides them. `processingInputRoot`/`processingOutputRoot` are unchanged:
  `rework_service.dart` still uses them to find the LWIP-input file a QC
  recapture must overwrite, and `processing_marker_service.dart` still writes
  `lwcam_capture_marker.json` into every transferred folder, which LWIP still
  waits for.
- The `processing_ledger` table, the `capture_folder_processing` sync entity,
  and the sink's `folderProcessingUpdateSql` case stay, but only to drain and
  apply a row a station had already queued before this change — nothing in
  LWCAM enqueues a new one.

--------------------------------------------------------------------------------
 2026-09-24 - LWIP: PRESERVE TILTED-PAGE BACKGROUND THROUGH QC DESKEW
--------------------------------------------------------------------------------

- `deskew_crop_file` now maps the final padded, straightened crop back into
  camera coordinates before cropping the JPEG. This retains the real photo
  background needed around a tilted page after QC rotates it.
- The rotated-frame guard trims only the side or sides that run into the camera
  frame boundary. A shortage at one edge no longer shrinks all four margins.
- Added regression coverage for a 2-degree page with enough capture background
  to retain 200px on every side after replaying the QC ops.

--------------------------------------------------------------------------------
 2026-09-10 - LUMINANCE CORRECTION OFF BY DEFAULT
--------------------------------------------------------------------------------

- `NodeConfig.luminanceEnabled` defaults to false (constructor, fromJson), and
  the QC engine's `luminance_enabled` likewise. Station Setup's switch starts off;
  LWCAM's toolbar hides the button when the config has not loaded. FamilySearch's
  standard is no manipulation and this is the one tool in the chain that is
  enhancement by definition; a project that wants it turns it on in Station
  Setup. An existing station picks the new default up at its next Station Setup
  save unless the switch was already saved on.

 2026-09-10 - LWIP: DESKEW IS NOW MEASURE-ONLY; ROTATION IS DEFERRED TO QC
--------------------------------------------------------------------------------

LWIP (deskew_crop_tool/image_ops.py, orchestrator.py)
- LWIP no longer calls cv2.warpAffine, ever. It still measures a page's tilt
  (the same side-fitting estimator as before) but the correction is recorded
  as an op list - `qc_ops`: `[{"op":"deskew","degrees":D},{"op":"crop","rect":
  [x0,y0,x1,y1]}]`, rect normalised 0..1 - for the QC engine to replay at
  preview and export time, once, on the one file that actually needs it.
  INTER_LANCZOS4 and the BORDER_CONSTANT black-fill are gone with it; they
  described a resample that no longer happens here.
- The crop box is now always the bounding rect of the UNROTATED contour plus
  padding (a tilted page's corners sit inside a bigger box, not a smaller
  axis-aligned one), so a tilted page is cropped exactly like a straight one -
  including down the lossless jpegtran path, which no longer depends on
  `angle` being zero. Every page is a lossless candidate now, not just the 49
  of 99 (at the 0.5 degree threshold) that needed no correction at all.
- `angle` in both the result dict and the manifest is now purely a
  MEASUREMENT (cv2 `getRotationMatrix2D` convention, 0.0 under
  deskew_min_degrees) - it no longer implies LWIP acted on it.
- Sign convention from source to the sign QC must replay, verified against an
  asymmetric fixture rather than assumed: `degrees = -angle`, replayed as
  `Image.rotate(-degrees, expand=True)` (== `rotate(angle, expand=True)`).
  Getting this backwards rotates a page a further ~2x its own tilt instead of
  straightening it - checked, not trusted, in
  `test_qc_ops_sign_convention_with_an_asymmetric_marker`.
- The crop rect is computed by replicating Pillow's own `rotate(...,
  expand=True)` geometry (rotate the frame's corners about its centre, take
  their bounding box, shift to (0,0), apply the same transform to the
  contour, pad, clamp) without ever calling it at full resolution - pure
  geometry, checked against real `Image.rotate` output in
  `test_qc_ops_replay_straightens_the_page` (residual < 0.15 degrees).
- Thumbnails (`_write_thumbnail_atomic`) replay the same `qc_ops` AFTER the
  512px downscale, so the QC rail shows a straight page at zero cost to the
  full-resolution file, which is never rotated. New shared
  `image_ops.apply_qc_ops(image, qc_ops)` backs the thumbnail, the tests, and
  `lossless_replay.py`, so the three cannot drift apart. `Image.rotate` does
  not support LANCZOS for an affine warp (confirmed against this runtime's
  Pillow - it raises); BICUBIC is what it offers, which is plenty at 512px.
- Manifest: every `files[]` entry gains `angle`, `lossless`, `qc_ops`, matched
  to its source by relative path (`ActiveFolder.image_results`, threaded from
  `_finish_image_job` through to `_publish`). Manifest `"version"` stays 1.
- Tests: 4 new (qc_ops replay, sign convention, thumbnail straightness,
  manifest fields) plus adjustments to the ones that asserted rotation had
  happened. 59 pass, 1 skipped (was 55 pass, 1 skipped).
- Verification: DEV\verification\lossless_replay.py now checks every page's
  lossless crop AND, for a page carrying qc_ops, replays them with Pillow and
  reports the residual angle.

ADDENDUM (same day) - the skew estimate is now self-consistent, and a page it
cannot settle on is left untouched rather than resampled on a guess.
- Finding on the 99 Control pages: a single `_page_angle` read over-estimates
  tilt on bound-register spreads by ~50%. Rotating by that estimate and
  re-measuring leaves a residual of median 0.31 deg, p90 0.60, with 9 of 50
  tilted pages over 0.5 deg. Re-measuring on the CROPPED output instead of the
  full frame barely helps (median 0.22). One correction pass - rotate by the
  estimate, re-measure, add the residual - gets to median 0.064, p90 0.41,
  only 3 pages over 0.5; those three oscillate instead of converging (residual
  flips sign across measurements, e.g. +1.087 -> -0.658 -> +0.551), so no
  angle from that sequence is trustworthy.
- New `_estimate_skew(image, contour, deskew_min_degrees)` replaces the single
  `_page_angle` call. Runs on the small DETECTION frame only (~1600px), never
  full resolution: up to 3 measurements, each after virtually rotating the
  ORIGINAL detection frame (`cv2.warpAffine`, `INTER_LINEAR`,
  `BORDER_CONSTANT` black - cheap at this size) by the cumulative estimate so
  far and re-detecting the contour; the first measurement reuses the contour
  the caller already found instead of re-detecting it. Every candidate total
  is kept paired with its own residual (the NEXT measurement); the candidate
  with the smallest residual wins.
- Stability gate: if the winning residual is >= 0.3 deg, or the contour
  disappears on a rotated frame, the page is left as captured - angle 0.0,
  qc_ops `[]` - and an INFO line logs the candidates that were tried.
  FamilySearch's standard is no manipulation, so an untouched 1 degree lean
  beats a confidently wrong 0.5 degree resample. `deskew_min_degrees` still
  thresholds whatever `_estimate_skew` returns, exactly as before.
- The crop box and qc_ops still come from the ORIGINAL, unrotated, full-frame
  contour - only how `angle` is measured changed. Cost bound: at most three
  small warps + contour passes, tens of ms.
- `_largest_content_contour` split into a scale-free `_largest_contour_in_frame`
  (the threshold/contour pipeline) so the estimator can re-run it on its own
  rotated detection frame without paying for another downscale.
- Tests: 3 new (`SkewEstimateTests` - clean-page accuracy, an erratic sequence
  returning 0.0/no qc_ops, a converging sequence picking the settled
  candidate over a later, unmeasured one). 62 pass, 1 skipped (was 59 pass,
  1 skipped).

 2026-09-10 - LWIP: LOSSLESS CROP FOR PAGES THAT NEED NO DESKEW
--------------------------------------------------------------------------------

LWIP (deskew_crop_tool/image_ops.py, tools\jpegtran.exe + jpeg8.dll)
- A page the skew estimator leaves unrotated (under deskew_min_degrees) is now
  cropped in the camera file's own coded blocks with libjpeg-turbo's jpegtran:
  no decode, no encode. The delivered pixels ARE the camera's - verified on the
  Control pages: interior of the crop window identical to the camera decode,
  max diff 0; quantization tables, EXIF and ICC are the camera's own. Only a
  page that is actually rotated still pays one Lanczos resample and one q100
  encode. Before, every page was decoded and re-encoded even when nothing but
  the crop changed.
- The crop box snaps OUTWARD to the 16 px iMCU grid (4:2:0), so up to 15 px
  more padding on the far edges, never less than asked and never into the page.
  Output dimensions therefore differ from the resampling path by up to 15 px.
- jpegtran runs with `-copy none` (drops every camera marker, including any XMP
  that could carry GPS) and the EXIF/ICC that _source_metadata already
  sanitised (GPS removed, Orientation 1) are spliced back in as APP1/APP2.
  Bytes go through stdin/stdout, so long paths never reach the tool.
- Not lossless, and deliberately so: EXIF Orientation 2..8 (cv2 rotated the
  frame on decode, so the box would not map onto the stored blocks), non-JPEG
  sources, non-.jpg outputs. Those take the resampling path unchanged.
- Fallback: tool missing or failing logs once and re-encodes as before. Override
  the tool location with LWIP_JPEGTRAN.
- Result dict gains `lossless` (bool) and `crop` [left, top, right, bottom].
- deskew_min_degrees default 0.2 -> 0.5 (image_ops.py, config/deskew_crop_config.json,
  LWCam Admin's lwip_config_writer). On the Control pages that moves 49 of 99
  onto the lossless path instead of 27; a 0.5 degree lean is ~2.6 mm on A4.
- Installer: tools\ ships with the LWIP tree; vcruntime140.dll is copied beside
  jpegtran.exe (LWSuite.iss).
- Tests: LosslessCropTests (4). 55 pass, 1 skipped.
- Verification: DEV\verification\lossless_replay.py runs every Control page and
  checks the lossless ones pixel-for-pixel.

 2026-09-10 - REWORK DUPLICATE-FILE GUARD; PARTIAL-SUBMIT GUARD; THUMBNAIL_PATH
 PARITY; RESERVED-NAME CHECK; EXPORTED CHIP REQUIRES isExported
--------------------------------------------------------------------------------

Five suspected defects investigated; all five confirmed.

Rework recapture (gallery_page.dart)
- `_startReworkRecaptureForSlot` checked only `target.parent.exists()` before
  waiting on a device photo. When QC's replace-image left a row's image_name
  pointing at a different extension than what is actually on disk (row says
  `IMG_0007.png`, folder holds `IMG_0007.jpg`), the check passed, the operator
  recaptured, and `_overwriteReworkFileAtomically`'s `rename()` onto a
  nonexistent target CREATED it - leaving both files in LWIP's input folder
  for it to publish as a duplicate page with no `capture_images` row. Now also
  refuses when the exact target file is missing, with a message that does not
  try to guess a sibling extension.
- Submit was enabled by `_reworkStaged.length + _reworkMetadataFixed.length ==
  0`, i.e. after closing even one of a folder's several open rework items.
  LWIP flips qc_status to PENDING on ANY file change, so a partial recapture
  (2 of 5 rejected pages) sent the folder back to QC with the other 3 still
  bad. New `reworkOpenItemCount` gates Submit on every open item being closed
  and the disabled button now shows the remaining count.

processing_report_service.dart / upload_stats_db.dart
- `thumbnail_path` was always written as `<output>/thumbs`, even when the
  manifest's `thumbnails.created` was false. LWIP's own writer
  (`cloud_report.py`) writes NULL in that case; the two writers of this row
  must agree bit-for-bit. `recordFolderProcessing`'s `thumbnailPath` param is
  now nullable and the service passes null when thumbnails were not created,
  both locally and in the `capture_folder_processing` outbox payload.

path_utils.dart
- `sanitizeWindowsName`'s reserved-device-name check tested the whole string,
  so `CON.1`, `NUL.txt` and `COM1.anything` sailed through unescaped even
  though Windows reserves the device name regardless of any extension. Now
  keys off the part before the first dot only (so `CONTOSO` is still fine).
  Fixes the keying-time preview in `folder_metadata_form_page.dart`, which
  calls this function directly, ahead of the batch failing at mkdir.

qc_task.dart / qc_home_page.dart
- `completedState` decided the "Exported" chip from `groupId` alone. A
  client-rework revert clears `is_exported` but KEEPS `group_id` (FamilySearch
  wants the correction republished under the same ID), so a reverted folder
  showed the green Exported chip with the old Group ID before the correction
  had shipped. New `QcCompletedState.reworkPendingExport` ("Rework pending
  export") requires `isExported`; the Group ID stays visible either way via
  the existing `completedIdentifier` fallback.

Tests: `reworkOpenItemCount` (test/pages/rework_helpers_test.dart), a
`thumbnails.created: false` case (test/services/processing_report_service_test.dart),
reserved names with an extension (test/services/path_utils_test.dart), and a
client-rework-revert case (test/models/qc_task_test.dart). 598 pass (was 592).

 2026-09-10 - ARCHIVE DATES PASS THROUGH VERBATIM; SEND BACK ONLY ON PASS
--------------------------------------------------------------------------------

Owner decision: capture_folders.start_date / end_date are TEXT in PostgreSQL
holding the archive date exactly as keyed ("1914", "1914-06", "1877-Mar-05").
The QC engine already stores and exports them verbatim; this app now does too.
(projects.start_date is a different column - the project's own start, still a
datetime - and is untouched.)

Sync (pg_statements.dart, pg_sync_sink.dart, pg_client.dart)
- `archivalDateOrNull` and `archivalDateText` are DELETED, with the
  year/year-month regex. They pinned a keyed date to UTC midnight on the way
  out and collapsed it back to its year on the way in - a value like
  "1877-Mar-05" or "circa 1918" became NULL. `folderUpsertSql` and
  `folderMetadataPatchSql` bind start_date/end_date as plain text (trimmed,
  blank -> NULL, via the new three-line `textOrNull`); `CAST(... AS
  timestamptz)` is gone from both and `kFolderMetadataDateColumns` with it.
  `tsOrNull` no longer falls back to year coercion - it is for event instants
  only. The rebuild snapshot SELECT drops its `::text` on the two columns.
- `CaptureFolder.fromRow` and the rework form's cloud seeding
  (gallery_page.dart `_reworkCloudFolder`) read the two columns as the strings
  they are; the "repair on read" that healed timestamptz renderings is gone
  with the type that produced them.

QC review (qc_review_controller.dart, qc_task.dart, qc_metadata_form.dart)
- `_text` (collapsed ANY parseable value in ALL 15 fields to its year - a
  Title or Volume that happened to parse was truncated too), `_wireValue`
  (expanded a 4-digit year to "YYYY-01-01T00:00:00Z" before POSTing) and the
  client-side start > end integer check in `blocksApproval` are DELETED.
  Values are shown and sent exactly as received. `QcMetadataField.isYear` and
  the "Year" helper text under the two fields are gone.

Template (batch_metadata.dart, metadata_template_test.dart)
- `kStartDateValues` / `kEndDateValues` are DELETED. Start/End Date follow the
  same rule as every other keyed field: dropdown when the project's template
  configures options, free text otherwise (the folder form already rendered
  per `TemplateField.isDropdown`). The standard template still seeds
  1914/1939 and 1918/1945 as ordinary option data; the parity test compares
  against those literals. Nothing in either app validates the fields as years.

QC Completed list (qc_home_page.dart)
- "Send back to QC" is shown only on rows whose status is PASS. The engine
  answers 409 for anything else (a REWORK folder is under capture rework); a
  409 that still comes back surfaces through the existing error banner.

Lint (qc_api_client.dart)
- `_send`'s 401 re-authentication retry now `return await`s inside its try,
  clearing the one non-baseline `unawaited_return_in_try_block` warning.

Tests: pg_statements_test drops the two archival-date groups; folderUpsertSql
binds "1877-Mar-05" unchanged with no CAST in the SQL, and " 1914-06 " / ""
round-trip to "1914-06" / NULL; folderMetadataPatchSql binds text with no
timestamptz. The approval gate's wrong-way-round test is replaced by one that
proves free-text dates are never ordered. dart analyze: 5 curly_braces infos
(baseline); flutter test: 592 pass (604 minus the 12 deleted coercion tests).

 2026-09-10 - LATE PROCESSING REPORT NO LONGER RE-QUEUES A PASSED FOLDER;
              A BOX'S DAY DIR IS DECIDED ONCE; MARKER IDENTITY GUARD
--------------------------------------------------------------------------------

Processing report vs QC (pg_statements.dart, LWIP cloud_report.py)
- `folderProcessingUpdateSql` and its LWIP transcription no longer set
  qc_status='PENDING' unconditionally. Both now write
  `CASE WHEN qc_status IS NULL OR upper(qc_status) IN ('', 'PENDING', 'REWORK')
  THEN 'PENDING' ELSE qc_status END`; the other five pipeline columns are
  written as before. The report can land days after LWIP finished: LWCAM's
  agent only runs while the app is open, so a folder completed after the
  operator closed LWCAM was reported by LWIP itself, approved and exported by
  QC, and then re-reported (fresh processing_ledger, new outbox row) when the
  app next opened - resetting the delivered folder to PENDING. LWIP's own
  NOT_YET/UNREACHABLE retries had the same window. Rework still re-enters QC:
  QC parks a folder in 'REWORK' before any recapture, and that state is in
  the allow-list. The two writers remain identical text (psycopg placeholders
  aside) - keep changing them together.
- The docstring's "re-enters QC even over an earlier PASS" (old decision 6) is
  superseded: a PASSed folder is only re-queued by QC's own send-back.

Transfer destination decided once per box (upload_stats_db.dart,
transfer_queue_service.dart, upload_controller.dart, capture_box_models.dart,
transfer_destination_service.dart)
- `markCaptureBoxTransferStarted` now takes the destination root, fixes
  `capture_boxes.transferred_to` = `<root>\<YYYYMMDD>` on the box's FIRST
  attempt and returns it unchanged on every retry (even days later, even after
  the station's root changed). The queue passes it to `uploadAll` as
  `destinationDir`; `retryUpload` reuses the batch's dir for box files. The day
  dir used to be `DateTime.now()` per run, so a retry across midnight copied
  the not-yet-recorded half of a folder into a second day dir; LWIP ran both as
  separate jobs with one identity and `folder_path` ended on whichever reported
  last, so QC opened half the pages. Normal Mode still lands on today's dir.
- Cloud `transferred_to` therefore now holds the day dir, set at transfer
  start; older rows hold the bare root, set on success. Nothing reads it
  (QC only declares the column). `CaptureBox.transferredTo` added.
- `markTransferred` no longer passes the root to `markCaptureBoxTransferred`;
  the parameter stays for tests. A legacy box finished through the fallback
  below keeps whatever it had (null, or the root).

Processing markers (processing_marker_service.dart, box_session_controller.dart)
- `writeBoxProcessingMarkers` writes into `<transferred_to>\<folderName>` only.
  The scan of every day dir for the folder NAME is gone for new boxes: it
  also matched a same-named folder from another box or another PC and stamped
  this box's identity into it. Boxes copied by an older build (transferred_to
  null or bare root) fall back to the old scan of the configured root
  (`legacyRoot`), so a box left "all copied, not yet marked" across the
  upgrade can still finish - marked `ponytail:` in the source, delete once no
  pre-2026-09-10 box is still OPEN.
- `_writeMarkerAtomic` refuses to overwrite a marker whose project_key /
  box_name / folder_seq differ from the payload (counted as a failed write, so
  the box stays untransferred with the message "another group or PC landed
  in <path>"). Same-identity rewrites stay idempotent; an unreadable marker is
  replaced.
- RESIDUE, documented not fixed: two capture PCs sharing one NAS root that key
  the same Volume on the same day still resolve to the same directory, and
  their images have merged by the time markers are written - the guard makes
  it visible (second PC's box stays partial) but does not prevent it.
  Folder-name uniqueness (`reservedFolderNames`) is local-DB only; there is no
  cloud folder-name cache like `cloud_box_names.dart` to check against.
  Distinct box names (which ARE checked cross-PC) do not help because the box
  name is no longer part of the folder directory name.

TESTS: pg_statements_test (+1: PASS is never reset), test_cloud_report.py
(assertion mirrors the CASE), sync_outbox_db_test (+1: day dir fixed once,
legacy root replaced), processing_marker_service_test (rewritten: persisted
dir only + decoy day dir ignored, foreign-identity refusal, legacy fallback,
missing/blank), capture_box_models_test (transferredTo). LWIP 49 pass 1
skipped; dart analyze unchanged (6 pre-existing); flutter test 604 pass.

 2026-09-10 - REVIEW FIXES: ORIENTATION TAG, LIVE-SYNC BASELINE, ENGINE RESTART
--------------------------------------------------------------------------------

Code review of the 2026-09-09/10 changes (LWCAM, LWCam Admin, two-PC LAN).

LWIP (deskew_crop_tool/image_ops.py)
- EXIF Orientation is now always written as 1, not only when it was the illegal

QC engine (Luminance Correction)

 2026-09-09 - AN UPGRADE NOW STOPS LWIP INSTEAD OF OVERWRITING A LIVE ONE
--------------------------------------------------------------------------------

Setup deliberately left LWIP running - a worker mid-folder, not a server - so
an upgrade replaced its .py files underneath a live process, which then kept
serving the code it imported at startup. Python closes a .py after reading it
and holds no lock, so the overwrite succeeds silently and Restart Manager
cannot see it. A station ran PRE-UPGRADE LWIP through two reinstalls that way
on 2026-09-09: q90 output and INTER_LINEAR from a process started before the
first install, while the files on disk were correct and every log looked clean.

Station Setup's save could not repair it either. startLwipNow only STARTS one,
and a live instance holds work_root\orchestrator.lock, so the replacement took
no lock and exited immediately - and LWIP reads its config once at import, so
saving new settings left the old ones in effect until the next logon. That is
the same defect the QC engine had, fixed the same way on 2026-09-04.

The drain itself already existed and was already correct: SIGINT/SIGTERM set
stop_requested, _cancel_unpublished drops every folder not yet publishing and
the one already publishing is allowed to finish. What was missing was any way
to REACH it. LWIP runs as pythonw.exe: no console, so no CTRL_BREAK; no window,
so `taskkill` without /F has nothing to post WM_CLOSE to; and /F is
TerminateProcess, which skips the handler entirely.

LWIP (backend/deskew_crop_tool/orchestrator.py)

- New stop-file channel, polled by the loop that already polls. Two locations
  are accepted: `work_root\stop.request` for a writer that has the config, and
  `%ProgramData%\LWCAM\lwip.stop` for one that does not - Setup, whose
  work_root sits under %USERPROFILE% and which cannot rely on an elevated
  install resolving the OPERATOR's profile. That directory is already created
  with users-modify by LWSuite.iss.
- The file is deleted as it is READ, not on exit. A stale one left by a crashed
  installer would otherwise make LWIP exit on every start - image processing
  would stop suite-wide with nothing in the log to say why, which is worse than
  the bug being fixed.

Installer (LWSuite.iss)

- New StopLwip(), called at ssInstall beside StopQcBackend(): writes the stop
  file, waits up to 90s for the process to go, then Invoke-CimMethod Terminate
  on whatever is left. Matched by COMMAND LINE against {app}\LWCAM\LWIP, never
  by name, so the QC engine and any other Python on the station are untouched.
- Terminate as the fallback is safe, and this was checked rather than assumed:
  every kill window recovers. work_root is rmtree'd per folder at admission, a
  stale .publishing is rmtree'd by its deterministic folder+hash name, an
  output published but not journalled is re-adopted by _try_adopt after a deep
  verify, and image writes land through a temp + os.replace so no partial file
  ever appears at the destination. Worst case is reprocessing one folder.

LWCamAdmin (services/lwip_autostart_service.dart, controllers/station_setup_controller.dart)

- New stopLwipNow(), and the save now stops BEFORE starting, unconditionally -
  turning processing off has to stop it too, not just unregister the autostart.
- It waits by acquiring LWIP's OWN orchestrator.lock (the same
  RandomAccessFile.lock pattern as FileLockService): getting the lock is proof
  the orchestrator has gone, and needs no process enumeration.
- On timeout the save does NOT start a replacement - that would spawn a process
  which exits on the held lock and look like success. It reports that
  processing is still busy and will start at the next logon.

- A stop request present at STARTUP is cleared and ignored
  (_clear_stale_stop_files, from _prepare_directories). A request can only be
  meant for a process that was already running, so one sitting there when this
  one starts is stale by definition.

  This was not theory. The first version of the change shipped to a station and
  took image processing down: Station Setup's save stopped LWIP, then started a
  replacement, and stopLwipNow had left its own request on disk - so the new
  process read it and exited 2ms after logging "Watching". Nothing else in the
  suite noticed. The Dart side now deletes its files in a finally, and this
  clears them anyway, because a silent stop is the worst failure this component
  has and one writer forgetting is not an acceptable single point.

TESTS: LWIP 46 passing, up from 42. Covers an absent file, consumption on read
(a second call is not a stop), a stale request from before startup being
ignored - the station regression above, as a test - and the property that makes
stopping safe at all: a folder dropped by a stop is reprocessed by the next run
rather than lost.

  LongPathsEnabled policy is locked off. Verified against Pillow,
  cv2.imread/imwrite and os.replace - cv2 matters because it does not use
  Python's file IO, which is what ruled out prefixing only Python's own calls.

- `_candidate_folders` still returns logical paths; only its per-child

 2026-09-09 - ARCHIVAL IMAGE FIDELITY: NO SECOND COMPRESSION, METADATA KEPT
--------------------------------------------------------------------------------

FamilySearch rejected every folder uploaded for the Taiping project: "Evidence
of image enhancement was identified in all folders uploaded ... ensure that any
compression, sharpening, or other image enhancement features are turned off."
The camera was not the cause. Replaying the shipped LWIP over the retained
originals reproduced all 99 delivered images (70 bit-exact, 29 within 13 DN),
and cropping a source at LWIP's own offset and re-encoding at q90 4:4:4

LWIP (backend/deskew_crop_tool/image_ops.py, config.py)

- Output JPEG quality is now 100, was 90. At 100 with 4:4:4 chroma libjpeg
  emits quantization tables of all 1s, the same tables the capture phone
  writes, so the processed page carries no more compression than the capture.
  Measured worst-case error against the source fell from 21 DN to 3, and the
  share of bit-identical pixels rose from 44% to 88%. Files are ~4x larger.
- EXIF and ICC now survive processing. The write moved from cv2.imencode, which
  cannot emit either, to Pillow. Every image LWIP has ever produced reached the

  dropped on the way through - it pins the building the records were
  photographed in - and Xiaomi's illegal Orientation=0 is normalised to 1.

  high-frequency detail retained against the unrotated original went from 0.48
  to 0.94 and Laplacian variance from 0.62 to 0.92. Ringing on a worst-case
  step edge is +0.12%, far below the camera ISP's own ~3% overshoot.
- Rotation fills exposed corners with black instead of replicating edge pixels.
  Smearing invented content into a record image is not acceptable, even where
  the crop usually discards it.

  degrees, which no handheld capture is ever under, so nearly every page paid a
  full resample to correct a tilt no reader could see.

  reported exactly 0.000 or 90.000 on page after page and deskew silently never
  ran, whatever the real tilt was. On the batch that exposed this the actual

  against a bound volume that IS tilted. Loose sheets are unaffected. An
  intermediate attempt using Hough lines over the whole frame was discarded: it
  locked onto cover texture and did not converge.

 2026-09-01 (later) - LWIP REPORTS FINISHED FOLDERS ITSELF
--------------------------------------------------------------------------------

A folder only reaches a QC operator once capture_folders.qc_status is 'PENDING',
and that write happened in exactly one place: the 15s ProcessingReportService
tick INSIDE this app. So an operator who transferred a box, closed LWCAM and went
on leave left the batch fully processed on disk and invisible to QC until someone
next opened the app on that PC. A week of leave was a week of stalled batches.

LWIP now writes that row itself. It already runs headless from logon, so it is
the process that is actually present when nobody is.

- BOTH writers stay. This app's report agent is UNCHANGED. The write is
  idempotent - identical columns, identical values, both derived from the same
  output manifest - so whichever arrives first wins and the other is a no-op.
  Verified on real data: the row LWIP wrote is byte-identical to the one the
  agent had already written.
- They cover different failures. LWIP's path survives LWCAM being closed; this
  app's outbox survives the station being offline, where LWIP cannot reach the
  database at all. Neither alone is enough.
- NodeConfig gains processingCloudReport (default true), in both apps' copies of
  the model - LWCAM can rewrite this file, and a key its model did not know would
  be dropped on that write, silently turning reporting off.
- LWIP's own default is false: a standalone START_DESKEW_CROP.bat run must never
  reach for a database. Station Setup writes true, which is how a managed station
  differs from a bare tool - the same split completion_marker and thumbnail_width
  already use.
- The retry never gives up. state.json outlives restarts, so a folder finished
  before a week-long outage reports itself when the network returns.
- NOT covered: a folder whose SOURCE is deleted while still unreported is pruned
  from state.json and lost. That means clearing a 1.Images day folder before QC
  has the batch - a housekeeping error either way, and no worse than before.

 2026-08-03 (later) — FOLLOW-UP REVIEW: 9 MORE FINDINGS FIXED
--------------------------------------------------------------------------------

A second review pass over the whole tree raised 9 findings. Two were holes left
by the 10-fix pass earlier the same day; the rest predate it, in the rework
loop, the login gate, and the DB corruption-recovery flow. Every claim was
re-verified against the code first — several were wrong in their details, and
two were worse than reported.

DATA LOSS: A RETRY COULD TRUNCATE AN ALREADY-VERIFIED, ALREADY-RECORDED FILE
- The destination name is allocated once per batch, and the copy opens it with
  FileMode.write (truncate-on-open). So any failure AFTER the durable commit —
  in practice reportCaptureImageTransferName returning false, which is
  deterministic and re-fires on every attempt — sent the retry back to re-open
  the good file and zero it. Worse, the previous pass's cleanup guard then
  (correctly) refused to delete the wreckage, so a truncated file survived with
  an upload_records row saying "verified".
- NOW: once the copy is committed, a retry redoes only the metadata step and
  never touches the bytes again.
- Also guarded the size-mismatch delete, the one cleanup path the earlier fix
  missed, and bounded the reconnect loop: an UploadInterruptionException used
  `continue`, which skipped both attempt++ and the cleanup, so an interrupt /
  reconnect cycle could repeat forever on the same attempt. Reconnects now have
  their own cap (10) and still don't consume one of the 3 attempts.

RECOVERY: "THE LOCAL DATABASE IS DAMAGED" WAS FIRED AT HEALTHY DATABASES
- inspectDeviceDatabase treated ANY exception as corruption. It opens the DB,
  and that open runs schema DDL which takes a write lock — so a concurrent box
  transfer, an AV scanner, or a WAL-lock timeout all produced a destructive
  rebuild offer on a perfectly good file.
- NOW: only genuine SQLite corruption signals count. Everything else is a new
  `unavailable` state meaning "try again in a moment".
- Fixed the inverse bug too. loadBoxes swallows its own errors, which made the
  page's corruption catch dead code AND meant a DB that failed real queries
  rendered as an EMPTY BOX LIST — indistinguishable from data loss to an
  operator holding un-transferred work. It now surfaces the failure.
- A missing DB on a fresh PC no longer offers "Recover capture history?".
- Index creation is best-effort per statement: an older file missing a column
  an index names skips that index instead of failing the open (a DB that won't
  open was exactly what got condemned as corrupt).

RECOVERY: THE REBUILD SILENTLY DISCARDED EVERYTHING THE CLOUD DIDN'T HAVE
- It repopulated only capture_boxes/folders/images and promoted the rest empty.
  sync_outbox was the serious one: an outbox row IS the un-pushed delta to PG,
  and the snapshot being restored comes FROM PG, so pending work existed
  nowhere else. A fully transferred box would stay 'OPEN' in the cloud forever
  and submitted QC rework closures would never land. replacement_records (the
  device's whole recapture audit history) and the legacy upload_records /
  daily_summary went too.
- NOW: those tables are carried over from the damaged file before promotion,
  best-effort and table-by-table, copying only the columns the two schemas
  share so an older file still contributes what it can. processing_ledger is
  deliberately still dropped — it self-heals from LWIP's state.json.
- The dialog said only "the damaged file will be kept as a backup", implying
  nothing was lost. It now states what is restored, what is carried over, and
  what cannot be recovered.

RECOVERY: THE PROMOTION RACED THE SYNC AND PROCESSING TIMERS
- Between evicting the cached handle and the final rename, the live path does
  not exist — and both timers reopen device DBs on the same isolate (sync every
  30s opens EVERY device's file as its first action, even offline; processing
  every 15s opens this one). A tick landing in that window had SQLite mint a
  new EMPTY database at the freed path, which blocked the rename; the rollback
  then skipped restoring the original because "a file already exists there",
  leaving the live DB empty while the UI reported "No local data was replaced."
- NOW: the DB layer refuses to reopen a device mid-promotion, the rollback
  clears an interloper before restoring, and the caller pauses both services.

REWORK: THE METADATA FORM WAS CORRUPTING ARCHIVE DATES
- start_date/end_date are timestamptz, so the driver returns a DateTime and the
  form was seeded with "1914-01-01T00:00:00.000Z" instead of "1914". The form
  has no date validation, so saving wrote that straight into the LOCAL row, and
  from there into the CSV and any re-transfer. (PostgreSQL itself stayed
  correct.)
- NOW: a new archivalDateText renders stored dates back to the keyed YYYY /
  YYYY-MM form, and CaptureFolder.fromDbMap routes both date columns through
  it, so rows corrupted earlier heal in place as they are read. Hand-keyed free
  text is never touched.

LOGIN: A BLOCKED DEVICE STRANDED A CAPTURE-ONLY OPERATOR
- The device-registry gate became async when it was added, but its callers were
  never updated. goToCapture fired it unawaited and returned true, so "Login
  Successful" had already shown and the session was already written when the
  block resolved — and no route was ever taken. The operator sat on the login
  page with a live session.
- NOW: goToCapture and enterCaptureWithProject are both async and both report
  whether entry succeeded; a blocked login clears its half-authenticated
  session, matching the existing no-project gate.

PASSWORDS: THE SHARED FILE LOCK WAS HELD ACROSS POSTGRESQL CONNECTS
- Each queued offline password change is retried against PG with a 5s connect
  timeout, and this ran INSIDE the lwcam_users.json lock, whose stale grace is
  30s with no heartbeat. About 7 queued entries pushed the hold past the grace
  period, at which point LWCam Admin deletes the lock as stale and both
  processes write the file — the exact interleaving the lock exists to prevent.
  Worst on a backlogged offline station, since the flush fires on every login.
- NOW: the PG retries happen before the lock is taken, matching what
  changeOwnPassword already did; only the re-read/splice/write is locked.

PERF: THE BOX LIST STALLED ~5s PER LOAD WHEN POSTGRESQL WAS UNREACHABLE
- loadBoxes awaited the rework-badge cache refresh, which opens a PG connection
  with a 5s connect timeout, before rendering anything. A cold offline open paid
  ~10s (the page loads twice) and a queued transfer paid 5s per box.
- NOW: the refresh runs off the render path and re-badges the list when it
  arrives. The counts only annotate and sort tiles.

SYNC: PER-BATCH BOX-ID CACHE NEVER HIT ACROSS ENTITY TYPES
- The box upsert cached under a 2-part key while lookups read a 3-part one

 2026-08-03 — WHOLE-PIPELINE REVIEW: 10 FINDINGS FIXED
--------------------------------------------------------------------------------

RELIABILITY/DATA-SAFETY: a full pipeline code review confirmed 10 issues, all
in LWCAM. All 10 fixed:

1. A committed-and-recorded transferred file could be deleted again by the
   retry cleanup's outer catch. upload_controller.dart now skips that cleanup
   entirely once durableCopyCommitted is true.
2. Duplicate box names across stations could silently merge one station's
   row into another's (the CloudBoxNames cache is advisory-only by design).
   The box/folder upsert SQL now carries an ownership WHERE clause
   (device_id = EXCLUDED.device_id) so a foreign row is never adopted; the
   sink surfaces the conflict (capped retry, loud error) instead of quietly
   continuing, and box creation does a best-effort live PG name check to
   shrink the race window.
3. A cloud users table that pulled back empty (outage, bad query) would wipe
   every local account. applySnapshot/writeSnapshotFile now keep the
   existing on-disk snapshot when a pull returns zero users.
4. migratePendingProcessingOutbox's SELECT-then-DELETE could drop a row
   enqueued concurrently by the still-armed processing report timer. The
   DELETE is now scoped to the exact ids just selected.
5. A stale queued offline password-change hash could replay over and revert
   a newer password. A successful direct password change now clears any
   earlier pending hash for that user.
6. Two writers in users_store_service.dart wrote the shared snapshot file
   wholesale with no cross-process lock, letting LWCam Admin's concurrent
   edits (including deletions) get resurrected. Ported LWCam Admin's
   file-lock protocol (lock, re-read disk, transform, write, release).
7. DECISION: the users/projects/app-settings refresh is no longer a switch —
   it runs every sync tick whenever a PG host is configured, full stop. It
   can no longer be disabled independently (this also un-wedges forced
   password changes on capture-sync-off stations).
8. An outbox row whose project/user/device couldn't resolve threw with no
   attempts cap, wedging the tick indefinitely. Resolver failures now cap at
   20 attempts, then skip-ack with a loud log, matching the existing
   skip-ack pattern used elsewhere in the sink.
9. Any exception escaping a sync tick (e.g. a torn outbox payload) reached
   the global handler and popped a crash MessageBox mid-transfer. syncNow()
   now wraps its whole body in a catch-all backstop: records the error,
   sets state=error, never rethrows.
10. DECISION: LWCAM no longer deletes an image once it has transferred —
    only the QC platform may. unassignImage refuses (and enqueues nothing)
    once transferred_name is set; the caller skips the local durable-copy
    delete and audit log on refusal too.

 2026-07-31 — CRITICAL: BOXES VANISHING AFTER AN ACCOUNT SWITCH
--------------------------------------------------------------------------------

FIX: ONE DEVICE'S QUERIES COULD RUN AGAINST ANOTHER DEVICE'S DATABASE
- Symptom (reported live): capture a box + folders + images on SAX04, log out
  without transferring, log in as SAX01, capture and transfer a box there, then
  return to SAX04 — the SAX04 box was GONE from the box list. It reappeared
  after an app restart; nothing was ever deleted (verified against both SQLite
  files: the SAX04 rows were intact the whole time, and its file had not even
  been opened during the failing session).
- Root cause (upload_stats_db.dart): the singleton held ONE Database handle plus
  a _currentDeviceId string, closing and reopening on every device switch. The
  id was assigned BEFORE the open completed, so two concurrent switches to
  different devices could finish out of order and leave the cached id naming one
  device while the cached handle pointed at ANOTHER device's file. From then on
  every getDatabase() for the "matching" id hit the fast path and returned the
  wrong database — loadBoxes' `WHERE device_id = 'SAX04'` ran against SAX01's
  file, found nothing, and the box "disappeared" for the rest of the session.
- Login is exactly that interleaving: auth_controller's SyncBootstrap.apply
  starts the drain, whose start() fires an UNAWAITED first syncNow() (opening
  the NEW device's DB), and the very next line's ProcessingBootstrap.apply runs
  migratePendingProcessingOutbox for the PREVIOUS device (opening the OLD one).
- Beyond the vanishing box, the same desync could have written NEW captures into
  the other device's DB file. Not observed in the reported run, but that is the
  dangerous variant and the reason this is filed as critical.
- NOW: handles are cached per device id (Map<String, Database> _deviceDbs) and
  never closed on switch — a station touches only a few (its operators' SAX##
  ids plus the 'PROCESSING' ledger), all WAL-mode, so holding them open is
  cheap and the race is gone by construction. A shared _cachedOpen helper adds
  single-flight opens (concurrent callers for the same key share ONE open
  instead of leaking a duplicate handle) and now backs the monthly-DB cache
  too, which had the same duplicate-open gap.
- Two workarounds this obsoletes: _ledgerConn (a private second handle that
  existed only to stop each PROCESSING-ledger touch from closing the capture
  device's DB) is deleted, and migratePendingProcessingOutbox no longer
  re-acquires its source handle per phase.
- Tests: test/db/device_db_handle_isolation_test.dart — concurrent opens for
  different devices each return their own file, same-device opens share one
  handle, a ledger write does not divert the capture device's handle, pending
  processing reports migrate between two live handles, and the reported
  scenario itself (a box captured on one device stays visible after the other
  device's DB is opened concurrently). All 5 fail against the previous code.

 2026-07-30 (last) — TIMESTAMP TIME ZONE, OUTBOX BATCH POISONING, POLL SPEED
--------------------------------------------------------------------------------

FIX: EVERY SYNCED TIMESTAMP WAS 8 HOURS IN THE FUTURE
- CAST(@x AS timestamptz) resolves a string carrying no offset using the SESSION
  time zone, and the `postgres` package pins that to 'UTC' on connect (its
  ConnectionSettings.timeZone default). The RDS server default is
  Asia/Singapore, so pg_statements.dart's claim that timestamps were
  "interpreted in the server's time zone" was simply false: LWCAM sends naive
  local strings, PG read them as UTC, and every row landed +8h.
- tsOrNull now converts real instants to UTC (.toUtc()). The local SQLite rows
  are deliberately NOT changed — they are also read back for local display, so
  the conversion belongs at the PG boundary, not at the source.
- NEW archivalDateOrNull for the keyed archive dates (start_date/end_date).
  These are wall-clock dates describing records, not instants, so they are
  pinned to UTC midnight of the date as keyed. A plain .toUtc() would turn
  "1914" into 1913-12-31T16:00Z — the WRONG YEAR once rendered — and would drag
  in historical offsets (Asia/Singapore was +07:20 in 1939, +09 in 1945).
- openPgConnection now states timeZone: 'UTC' explicitly. Redundant while
  nothing emits a naive string, but it stops a future change to the package
  default from silently reintroducing this.
- Was already fixed for rework_logs.closed_at alone, because
  selectOpenReworkSql orders on it and a future-dated CLOSED row would have
  hidden a genuine re-rejection for 8 hours. Everything else is fixed now.

FIX: ONE BAD OUTBOX ROW NO LONGER STARVES ITS WHOLE BATCH (handover §7.9)
- PgSyncSink.apply wraps a batch in ONE transaction, so any row that threw
  rolled back the healthy rows with it: nothing was acked and _backoff bumped
  attempts on every record. Up to batchSize rows sat behind one poison row on a
  backoff capped at 15 minutes, indefinitely.
- SyncService now retries a failed batch ONE ROW AT A TIME (_applyIndividually),
  acks each that succeeds and backs off only those that still fail. The batch
  transaction is kept for the happy path, so the isolation pass costs nothing
  until a batch has already failed. Re-applying a row that had succeeded inside
  the rolled-back transaction is safe — every statement is an idempotent upsert
  or an append-only rework_logs insert.
- A SyncConnectException aborts the pass: an unreachable destination means the
  remaining rows are pending, not poison.
- Side effect: the 20-attempt skip-ack paths (processing reports, rework
  closures) now behave as documented. Previously a sibling row's failure
  inflated their attempts, so they could skip-ack early through no fault of
  their own.
- A transient one-off batch failure now recovers within the same tick instead
  of leaving rows pending — three sync_service tests were updated to model a
  genuinely bad row (FakeSyncSink.alwaysThrow) rather than a single error.

CHANGE: RECAPTURE DETECTION POLLS AT 350ms, NOT 2s
- Both recapture flows (pre-transfer slot swap and rework) passed no
  pollInterval to _waitForNewCapture, taking the 2s default. The
  shutter-triggered expedited sync cannot help them, because
  _syncNewDeviceImages returns immediately while _isWaitingForRecapture is true
  — deliberately, so a recapture in flight is never ingested as a new
  standalone image. That poll IS the detection latency.
- Both now pass kExpeditedSyncInterval (350ms), saving ~1s average and ~1.65s
  worst case of a measured 8.3–11.7s round trip. The remaining cost is the
  ~15MB adb pull and the ~50MP JPEG decode, not the poll.

- The overwrite changes the folder's input fingerprint, so LWIP reprocesses
  the whole folder, the report agent re-reports it, qc_status returns to
  PENDING, and the folder is back in the QC queue. No new transfer, and the
  transferred box stays read-only throughout — recapture never reopens it.
- Closure is APPEND-ONLY: after the file is written, LWCAM queues a CLOSED
  rework_logs row through the outbox (so an offline recapture is not lost).
  rework_logs is never UPDATEd; "still open" means the LATEST row for an
  image is OPEN. QC approve deliberately does not close rows.
- New services: rework_service.dart (PG read + input-path mapping),
  recapture_service.dart (camera/ADB — a copy of the gallery_page machinery;
  that file stays untouched, per the house rule).
- New outbox entity 'rework_logs' (last in kSyncEntityOrder) with natural-key
  resolution in the sink, so retry/backoff comes free.

NOTES
- Reprocessing is WHOLE-FOLDER: QC edits already saved on that folder's other
  images are regenerated away and must be redone at re-review. LWIP has no
  per-image mode.
- Recapture only works on the station that captured the folder — a folder
  outside this station's output root is refused rather than guessed at, which
  would clobber an unrelated image.

Findings from a three-way review (cross-app contracts, LWCAM sync/auth,
LWCam Admin) — all verified against the code before fixing:

- FIXED (major): the sync pull no longer overwrites a lwcam_users.json that
  LWCam Admin has marked dirty (offline edits/delete-tombstones queued but
  not yet pushed). Both apps share this file on a standard station; the
  pull predates those edits, so overwriting silently destroyed them — a
  user deleted offline could resurrect. LWCAM's UsersStore also now
  round-trips the Admin-only JSON keys (dirty/tombstones/pending resets)
  opaquely through its own writes instead of stripping them.

- FIXED (major): a forced password change / login stamp now sends the
  CANONICAL username (the store record's) to PostgreSQL, not the typed
  one. Local lookup is case-insensitive but PG matches user_id exactly —
  typing "ALICE" for record "alice" made the password UPDATE a silent
  0-row no-op (and marked a queued offline change delivered when it
  wasn't; the change then evaporated on the next pull).

- FIXED (major): UsersStoreService now serializes all pending-file/
  snapshot read-modify-writes behind an internal mutex. The unawaited
  login-time flush racing the forced-change dialog could drop a
  just-queued password change (read-modify-write on shared files with no
  locking).

- FIXED (minor): changeOwnPassword queues on ANY PostgreSQL failure, not
  just the explicit "unreachable" error — a connection that opened but
  died mid-write previously blocked the operator instead of queueing. The
  queued retry is idempotent even if the original write actually landed.

- Docs: stale comments in upload_stats_db.dart still described sink
  resolution by project_id; corrected to project_key.

- Cross-app (see LWCam Admin's CHANGELOG for its side): schema gained
  partial unique indexes so soft-deleted rows no longer block reuse of
  device IDs / project IDs / project names — DROP AND RECREATE the
  PostgreSQL database from the updated SQL file.

- NodeConfigService gained reload() (re-read from disk, bypassing the
  cache); the Settings Sync section now reloads before editing so a save
  can't write back a config LWCam Admin changed after LWCAM first loaded
  it (both apps share lwcam_node_config.json).

- A forced first-login/reset password change no longer blocks when
  PostgreSQL is unreachable. Previously it refused with "connect to the
  sync database and try again" — fine for a flaky connection, but a real
  problem for a site that is permanently offline. Now: PG is still tried
  first, but on failure the new password is applied to the local snapshot
  right away (so the operator can log in this session) and queued in a new
  sibling file, lwcam_pending_password_changes.json (username → new bcrypt
  hash). Every sync tick and every subsequent login attempt retries the
  direct PG write; until it lands, every pulled snapshot has the pending
  hash re-spliced onto it so a stale pull can never silently revert the
  change. The operator sees "Saved on this device — it will sync to the
  server once reconnected" when the change had to be queued.

REWORK MODE - AUDIT FOLLOW-UPS (structural hardening)
- Torn-write recovery for shared sidecar files: a 0-byte manifest or box
  claim left by a crash between create and write (which previously bricked
  the batch root / box with unhandled exceptions on every PC) is now healed
  on the next attempt, guarded by a 10-second grace period so recovery can
  never steal a reservation that is being written at that moment.
- Reconciliation is now bidirectional: when this operator is the box's
  assignee and the local DB is ahead of the share (a status write lost to a
  share blip, or a status doc lost to a crash), refreshBoxes rewrites the
  doc from local truth — a missed markTransferred can no longer persist as
  permanent cross-operator desync (RW-34).
- Bulk shared-state reads (box claims + task statuses) now run with bounded
  parallelism (16 concurrent) and an mtime+size cache, so a box-list
  refresh at full scale (~1,200 sidecar files on SMB) re-reads only changed
  files instead of serially re-reading everything on every navigation.
- New "delete photo" action (trash icon on each capture tile, with a
  confirmation): permanently removes the photo from the phone (adb rm), the
  local cache, and this task's grid, and retires its claim (kept as
  superseded so the resumed grid never re-pulls it and no other task can
  reuse the filename). Use it to discard a shot taken on the wrong task or
  an unwanted photo — re-shoot if needed. (This replaced an earlier
  release/re-link recovery action; deleting-and-reshooting is the simpler
  model for physical-document rework, and since the file leaves the device
  the live poller can't re-claim it.)
- Checkpoint/resume made real for rework transfers (it was inert in both
  modes: every batch pre-created an empty, per-run-timestamped checkpoint it
  could never find again). Rework checkpoints now use a stable name per
  capture ID, record a queue signature (resume only over the exact same
  file set), checkpoint the highest CONTIGUOUS completed index (a mid-batch
  failure can no longer be skipped forever on resume), and are deleted
  after a fully successful transfer. Normal Mode behavior is unchanged

FIX: REPLACE-IMAGE CAMERA LAUNCH (gallery_page.dart)
- Problem: clicking "replace" launched the phone camera, which immediately
  closed itself. Cause: on Xiaomi HyperOS 3 (MIUI Camera 6.4+), the camera
  rejects the VOICE_COMMAND quick-launch intent from adb as an "illegal
  caller" and finishes itself - while `am start` still exits 0, so the
  working fallback strategies never ran.
- Reordered launch attempts so the micamera:// Pro-mode deep link (verified
  working on HyperOS 3) runs before the VOICE_COMMAND shortcut.
- Launch attempts are now verified: after each `am start` that reports
  success, the app polls the phone's foreground activity (600 ms interval,
  up to ~6 s) and only trusts the attempt once the camera actually stays on
  screen; otherwise it falls through to the next strategy. Polling (rather
  than a single early check) prevents a slow cold start from being misread
  as a self-close, which previously caused the camera to flash open/closed
  twice before settling.
- Added Pro-mode detection: before launching, the app checks whether the
  camera is already in the foreground with the Pro module active (reads the
  camera's own enterNewMode log events, filtered to the current camera
  process PID). Camera already in Pro mode -> left untouched; in another
  mode -> switched to Pro; closed -> launched into Pro.

FEATURE: SWAP-IN-PLACE REPLACEMENT (gallery_page.dart, upload_stats_db.dart)
- Replacing an image now deletes the erroneous original from the device.
  After the new capture is pulled and verified, on the device: original is
  renamed to a .bak sidecar -> capture is renamed over the original's
  filename -> .bak deleted. If any step fails the .bak is restored, so the
  slot can never lose both images; on failure the app falls back to the
  previous overlay behavior (original kept, replacement shown on top).
- Result: the device holds only the corrected image, under the original's
  filename. Slot position/numbering is preserved, and the erroneous image
  can never be part of a transfer.
- The local gallery cache mirrors the swap (corrected bytes copied over the
  original's cache file, tile thumbnail and preview refreshed in place).
- Replacement records with type 'recapture-swap' are pure audit records;
  restore-after-restart no longer needs overlay state for them.

FEATURE: FULL REPLACEMENT HISTORY IN DB (upload_stats_db.dart)
- New column replacement_records.superseded_at (added automatically to
  existing databases on first open).
- Replacement records are never deleted anymore: replacing the same slot
  again marks the earlier record superseded instead. The full chain
  (captured -> replaced at T1 -> replaced again at T2) is traceable per
  slot, including operator and timestamps.
- getReplacementRecords() now returns active records by default;
  pass activeOnly: false to read the full history.
- New methods: markReplacementRecordsSuperseded (all records of a slot),
